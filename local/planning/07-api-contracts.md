# API Contracts

CTA buttons are a hard v1 requirement, so the wire shape they travel over needs to be concrete and
written down, not left implied by prose elsewhere in this planning set.

## POST /chat

Phase 1 ships this non-streaming. Phase 4 adds `/chat/stream` as the SSE variant of the **same**
underlying turn — both routes call one shared internal function (`05-setup.md`'s "One turn function,
two transports"), so this contract describes both; streaming just delivers the same final shape
incrementally.

### Request

```typescript
{
  message: string;
  siteId: string;
  sessionId: string;   // generated by the widget, held for the life of the browser tab/session
}
```

### Response

```typescript
{
  responseText: string;
  clientActions: ClientAction[];   // [] when there's nothing to offer — always present, never omitted
  sessionId: string;
}
```

`responseText` and `clientActions` are independent, not alternatives — see `01-architecture.md`'s
"Navigation / CTA design." A turn with a good knowledge-base answer *and* a matching route returns a
full `responseText` and a `navigate` action in the same response; a CTA is never a substitute for the
text answer, and the text answer is never withheld just because a CTA is also being offered.

## ClientAction

```typescript
type ClientAction =
  | { type: "navigate"; path: string; label: string };
  // Phase 6, reserved — not implemented, not sent, not read by the widget yet:
  // | { type: "render_items"; layout: "list" | "cards" | "table"; items: RenderItem[] };
```

- **`navigate`** is the only action type that exists in v1. `clientActions` holds zero, one, or a few
  `navigate` entries, matching the tiered CTA design (single / branch / none).
- **`path` always comes from a `SiteRoute` row's own `path` column — never text the model composes
  freely.** This is a deliberate, load-bearing invariant, not an implementation detail: the model's job
  is choosing *which* retrieved route candidate(s) to surface, never *what path to write*. A `navigate`
  action whose destination the model could influence directly would reintroduce exactly the failure
  mode this design exists to avoid — a confidently wrong suggestion that looks identical to a correct
  one until a visitor actually clicks it.
- `render_items` (or whatever Phase 6's structured-response type ends up named) is listed here only as
  a placeholder so the union has a known extension point when that phase starts — it carries no
  behavior yet and the widget doesn't need to handle it until it's actually built.

## Internal endpoints (admin → API)

Mirrors the pattern of the request/response shapes above — not fully specified yet, since the admin
panel is Phase 5. Worth deciding before that phase starts, not during it: document upload (→ ingestion
pipeline, `02-rag-architecture.md`), route CRUD, site CRUD, and conversation-log listing all need their
own small contracts here, added to this file as each is built rather than left implicit in route code.
